# Ideas, October 2026

Follow-up on HANDOVER.md's "Ideas noted, not started" (05/10): the
multimedia beacon on real data, Q65, JS8Call, and a signed self-update
feed. The first two are done or built; JS8Call and the update feed are
assessment/design only, as asked.

## Q65 - done (receive and transmit)

Built: `ohscore/modes/q65.py` (its own module, not folded into `ft8.py` -
see its docstring for why), wired into the mode registry
(`ohscore/modes/__init__.py`), NB's mode list and TX slot timing
(`ohsnb/state.py`, `ohscore/engine.py`'s `SLOT_SEC`/`SLOT_LEAD`/`SLOT_LATE`),
the bandplan's signal width and mode class (`ohsnb/bandplan.py`, plus a
"Q65-60A" preset at 10489.545 MHz in the narrow-digimodes segment), and
the ADIF logbook mapping (`ohscore/logbook.py`). Tests:
`tests/test_modes_q65.py`, in test_modes_ft8.py's style.

**jt9 can decode it and q65code can encode it** - checked directly against
Debian's `wsjtx` 2.7.0+repack-1 (the same package FT8/FT4 already use):
`jt9 -3`/`--q65` plus `-b <submode>` and `-p <period>`, and `q65code "msg"`
for the channel symbols. Confirmed by generating a Q65-60A signal two
ways - WSJT-X's own `q65sim`, and this module's own encoder - and decoding
both with `jt9 -3 -p 60 -b A`.

**Submode and period: Q65-60A**, cited to WSJT-X's own "Quick-Start Guide
to Q65" (K1JT, G4WJS, K9AN, IV3NWV; wsjt.sourceforge.io/Q65_Quick_Start.pdf).
No on-air convention for QO-100 NB specifically was found - the existing
`docs/qo100-research.md` already marks Q65 "[unverified]" for even a
calling frequency, and a web search for "Q65-30A"/"Q65-60A" plus QO-100
turned up nothing. So this is a reasoned choice, not a measured one:
- **Submode A** (the narrowest tone spacing at every period, 1x; B-E are
  2x/4x/8x/16x) is what the Guide's submodes B-E exist for: Doppler
  spread and multipath (its own worked examples are all troposcatter,
  ionoscatter, rain scatter and EME - every one a path with real
  frequency spread). QO-100's narrowband transponder is a geostationary
  bent pipe to a fixed ground station - the LNB drifts (see the beacon's
  own rxCorr log, a few Hz over tens of seconds) but nothing spreads the
  tones the way a moving target does, so there is nothing for B-E to buy.
  A's occupied bandwidth at every period is also comfortably inside the
  bandplan's "narrow digimodes (<=500 Hz)" segment (10489.540-.580 MHz).
- **Period 60 s**: deep enough to be worth having alongside FT8 (-27.6 dB
  vs FT8's roughly -20 to -24 dB, same Guide, same 2500 Hz convention)
  without a single exchange taking the 5+ minutes 300 s would. No QO-100
  precedent found either way.

**Output format differs from FT8/FT4's**, measured directly (not assumed):
jt9's `-3` stdout line has the same shape as `-8`/`-5`'s (leading field,
SNR, DT, df, marker, text) but the leading field is not a reliable
six-digit clock (seen "0000" and "****" depending on the WAV's name -
discarded either way, as FT8/FT4's six digits already are), the sync
marker is ":" rather than "~"/"+", and the trailing quality flag is the
Quick-Start Guide's "q0".."q4" (optionally a second digit: periods
averaged) rather than FT8/FT4's "a1".."a7"/"?". `ohscore/modes/q65.py`
has its own regexes for this; `ft8.py`'s are untouched.

**Not done:**
- **Averaging across periods.** WSJT-X's own worked example in the
  Quick-Start Guide needed three periods averaged before a weak signal
  decoded - a real part of Q65's advertised sensitivity, and a different
  interaction model from FT8/FT4's "decode this slot, now" that this
  first cut deliberately did not take on. Tried instead: pushing noise
  hard enough in one 60 s period to find where a-priori help (MyCall/
  DxCall) made the difference, the way `test_modes_ft8.py`'s
  `Jt9CallsTests` does for FT8 - it did not show a margin at any noise
  level tried (decoded cleanly up to a point, then failed for both with
  and without AP), which fits: the Guide's own AP demonstration needed
  averaging to get into that margin at all.
- **Transmit waveform shaping.** `_tone_audio` in `q65.py` switches
  tones abruptly (continuous phase, no Gaussian smoothing) rather than
  reproducing WSJT-X's own Q65 modulator; checked against jt9 -3 and it
  decodes cleanly at a clean SNR, but WSJT-X's own tones are very likely
  shaped for a tidier transmitted spectrum, which matters more here than
  usual - other QO-100 NB traffic sits either side in only 40 kHz. Worth
  a closer look (reading `gen_q65wave.f90` if WSJT-X's source is fetched
  for reference) before this transmits for real.
- **No UI yet.** `ohscore/ui/panels/ft8.py` (the slot-mode sequencer
  panel, waterfall labelling in `ohscore/ui/window.py`'s `label_event`)
  is hardcoded to `("ft8", "ft4")`; Q65 decode/transmit works end to end
  through the engine (`radio.set(mode="q65")`, `radio.send("q65",
  text=...)` - checked against the simulator) but has no waterfall
  labels and no CQ/reply/report sequencer of its own yet. That UI work
  - plumbing through a third slot length and Q65's own "q#" flags - is
  the next piece, not attempted here to keep this one change reviewable.
- **No submode/period chooser.** Fixed at 60A; a setting is cheap to add
  once Brian has an opinion from using it.

## JS8Call - receive built (07/10/2026); transmit still not started

**Since this assessment was written, JS8 Normal receive is built**:
`ohscore/modes/js8.py`, wired into the mode registry, NB's mode list,
bandplan (the existing "JS8Call" preset's mode is now `js8`, and it has a
mode-spot like Q65's) and the ADIF mapping, the same shape as Q65's own
wiring. Tests: `tests/test_modes_js8.py`. The assessment below is kept
as the reasoning this was built from; two things it did not anticipate,
found while building it:

- **`js8`'s own period option is a red herring.** Its `-p MINUTES` only
  accepts a short fixed list (1/2/5/10/30) that has nothing to do with
  JS8's actual 6/10/15/30 s sub-mode periods - checked against js8call's
  own regression WAVs (`media/tests/*.wav`, 2.2.0+ds-5+b1): a submode-A
  file is exactly 15.000 s, and the CLI's own default (no `-p` at all,
  exactly as js8call's own `test` script calls it) decodes it correctly.
  `ohscore/modes/js8.py`'s module docstring has the measured format string.
- **Most of what `js8` decodes is not human-readable - a bigger gap than
  assumed.** This assessment expected "wiring JS8 receive ... would very
  likely follow q65.py's pattern" for the output format, which was right,
  but did not anticipate that js8's *message content* needed a second
  unpacking layer: unlike jt9's own Q65/FT8 decode (which unpacks a
  message to text itself), JS8's `lib/decoder.f90` only does that for
  "CQ ..."/"DE ..."/"QRZ ..."-shaped standard messages; everything else -
  directed replies, compound calls, heartbeats, data messages, which is
  most of JS8's actual on-air traffic, confirmed against js8call's own
  test WAVs - comes back as a packed token in its own ~2200-line
  "Varicode" alphabet (`varicode.cpp`/`decodedtext.cpp`, the GUI's own
  code, not the Fortran decoder's). This module does not unpack that
  layer: `text` is always set to whatever `js8` printed (as ft8.py/q65.py
  already do for non-standard messages), so a packed frame shows as its
  token rather than a wrong guess, not as nothing. Unpacking it is its own
  mode-module-sized job, same scale as the encoder cost already estimated
  below, just found to apply to decoding too - a clear next phase, not
  done here to keep this change the size the task asked for.
- **No Windows build.** js8call is its own project with its own Windows
  DLL set, not inside WSJT-X's installer this Windows build already
  bundles: adding it needs its own entry in
  `packaging/windows/sources.txt` with its own verified upstream tarball,
  not attempted here (docs/INSTALL.md "JS8 on Windows").

Original assessment, 05/10/2026:

### JS8Call - assessment only, no code

**There is a usable decoder outside the GUI.** Debian's `js8call`
2.2.0+ds-5+b1 installs two binaries: `js8call` (the Qt GUI) and `js8`
(`/usr/bin/js8`) - a standalone CLI decoder of exactly jt9's own shape
(`js8 --help`: reads WAV files or a shared-memory key, `-8`/`--js8` for
JS8 mode, `-b` for its sub-mode A-E, `-c`/`-x`/`-G`/`-g` for a-priori
calls and grids, `-p` for the T/R period in minutes). JS8Call is
WSJT-X's own fork (its copyright file: "Copyright (C) 2001-2018 Joe
Taylor... 2018-2019 Jordan Sherer, KN4CRD"), so this is the same family
of tool as `jt9`, not a different interface to learn - wiring JS8
receive through it would very likely follow `ohscore/modes/q65.py`'s
pattern (and, as with Q65, its own output format would need checking
directly against a real decode rather than assumed from jt9/q65's).

**There is no equivalent CLI encoder.** `ft8code`/`ft4code`/`q65code`
each have one; the `js8call` package ships none - JS8's message packing,
Varicode compression and its own framing live inside the GUI binary (or
inside `js8` with no CLI entry point exposing them). This matches what
`docs/digimodes-rust.md` already found reading JS8Call's source for
`rust/ohsdigi`'s module boundaries (05/10/2026): JS8 adds a CRC-12
layer, reuses FT8's (174,87) LDPC code, and needs a message layer and
modulator of its own - "nothing of JS8 is implemented" there yet,
and that document already earmarks JS8 as the next mode after FT8/FT4
(and now Q65).

**Licence**: GPL-3.0-or-later (JS8Call's own copyright block, same
family as WSJT-X's own GPL-3 - HANDOVER.md: "Licence GPLv3, so GPL code
... may be borrowed with attribution"). No licence obstacle either way.

**Cost**: receive-only, through `js8`, is about the same size of job as
Q65 was here - a new `ohscore/modes/js8.py`, its own jt9-family output
parsing checked against a real decode, mode-registry and bandplan
wiring. Transmit needs porting JS8's modulator (Varicode, its CRC-12,
the shared LDPC(174,87) table, framing per sub-mode) into `rust/ohsdigi`
first - a project in the same class as the FT8/FT4 port that
`docs/digimodes-rust.md` already describes, not a cheap add.

**Recommendation**: worth doing, in two phases, not one. Receive-only
via `js8` first (cheap, same shape as every jt9-family mode here now);
transmit only once `rust/ohsdigi` grows a JS8 encoder, which is squarely
`docs/digimodes-rust.md`'s own next phase rather than a new idea. Not
done now because it is a second full mode module's worth of work (jt9
output format work alone was non-trivial for Q65) and this session's
budget was Q65 plus this assessment, not a second mode.

## Signed self-update feed - design only, no code

**Since built (07/10/2026), with Brian's decisions in place of the open
questions below:** a new, dedicated key rather than the Azure identity;
checked on start-up and daily, on by default, rather than opt-in; one
feed per app; Linux runs `pkexec apt-get install` itself. The contract is
`docs/update-feed.md`; the note below is kept as the reasoning it came
from.

NB and HAM are already published at `openhamshacknb.brian-henderson.co.uk`
and `openhamshackham.brian-henderson.co.uk` from `/srv/openhamshack-{nb,ham}-releases/`
(HANDOVER.md "Publishing"): that folder *is* the site, `tools/release.sh`
writes `<pkg>_<ver>_<arch>.deb` + `.sha256` sidecars there and, after
`--windows`, a signed `<pkg>-<ver>-setup.exe` + `.sha256` beside it.
Nothing machine-readable describing "what is the latest version" exists
yet - only the human `index.html` and the files themselves - so a client
checking for updates needs one new thing: a small manifest, plus the
code in NB/HAM to read it, verify it, and apply it.

### Trust model

- **Signing key**: not a new one. Windows `.exe`s are already Authenticode-
  signed (HANDOVER.md "Signing": Azure Artifact Signing as "360
  Technology", via `packaging/windows/sign.ps1`); Windows's own
  `WinVerifyTrust` is the existing, already-deployed verification for the
  installer itself. What is missing is signing the *manifest* (the small
  file saying which version is current and what its hashes are) so a
  client can trust *that* before it trusts anything the manifest points
  at - otherwise a manifest swapped in transit or on a compromised host
  could point a client at an old (vulnerable) signed installer, or at
  one for the wrong app, and the Authenticode check alone would not
  catch either. A second, small key is simpler than reusing the Azure
  Trusted Signing identity for this: the manifest is signed far more
  often than installers are (every release, read by every client on
  every check) and from a different context (the release machine
  writing to `/srv/...`, not the signing SYSTEM task over SSH), so an
  Ed25519 keypair kept on shack (private half readable only by whatever
  user runs `release.sh`) signing the manifest file itself is a clean
  addition, not a change to the Authenticode path.
- **The .deb has no established signature scheme here.** `apt`'s own
  (a repository `Release` file signed by a key apt trusts) is the
  standard answer but means standing up a real apt repository instead
  of a folder of loose `.deb`s - a bigger change than the manifest idea
  needs. The manifest's own signature covering the `.deb`'s sha256 (the
  sidecar file `release.sh` already writes) is enough for a client that
  checks the manifest's signature and then the file's hash against what
  the manifest says: the loose-file layout stays exactly as it is.
- **Verification**: the client ships the public key (baked into the
  package, as the Windows build already ships libiio/WSJT-X's files -
  HANDOVER.md's `packaging/windows/sources.txt` pattern) and checks the
  manifest's signature before reading anything in it, then checks the
  downloaded file's sha256 against the manifest's before running or
  installing anything. A manifest that does not verify is treated as
  "no update available", logged, never surfaced to the operator as a
  decision to make.
- **Rollback**: `.deb`s already never get removed (HANDOVER.md: "older
  `.deb`s stay") - downgrading now is `apt install
  openhamshack-nb=<version>`. Windows's installer is Inno Setup; the same
  policy (never delete an old one from `/srv/.../_-archive/`) already
  exists for retired installers, so a client-side "roll back" is
  "re-run last known-good .exe", which a self-updater can offer without
  new infrastructure if it keeps the previous installer it downloaded
  (one copy, replaced on the next successful update) rather than
  deleting it the moment the new one installs.

### Linux (.deb)

A systemd timer (or a menu item - "Check for updates", matching "opt-in"
below) runs a small script: fetch the manifest, verify its signature,
compare `ohsnb/VERSION`'s content against the manifest's version for this
app, and if newer, fetch the `.deb` named there, check its sha256 against
the manifest, then `pkexec apt install ./the.deb` (or hand the operator
the command rather than running it, depending on what "opt-in" is asked
to mean - see below). No root is needed for the check itself, only the
install step, which is a named privileged operation same as everything
else in Dock360's house rules, even though this is not Dock360 - "root
needs a validated verb" is good practice regardless of project.

### Windows (signed .exe)

Same manifest, same signature check, but the install step is simpler to
reason about because the file is *already* Authenticode-signed: the
updater's job is only to fetch the manifest, verify it, fetch the right
`.exe`, check its sha256 against the manifest (belt and braces - the
Authenticode signature is the real guarantee once Windows checks it,
but confirms the download was not truncated/corrupted before that),
and run it (Inno Setup's silent-install switches, or just open it and
let the operator click through - the existing manual install already
needs "close any running OpenHamShack NB or HAM first", which a self-updater
would need to ask for or handle itself, e.g. by refusing to run while
the app is open rather than trying to kill it).

### Privacy

No telemetry: the check is a GET of a small, static, public file (no
query string beyond the cache-busting `?v=` HANDOVER.md already uses for
verifying an upload) from the same 20i-hosted site the installer itself
comes from - nothing about the requesting machine travels with it beyond
what any HTTP request already carries (IP, user-agent), and nothing is
logged or reported back about what it found. Worth saying plainly in the
guide, since "phones home" is exactly the kind of thing this project's
audience (amateur radio operators, often privacy-conscious about a
program with a working TX chain) would otherwise reasonably ask about.

### Opt-in

Off by default; a setting (`checkForUpdates`, matching the house style
of every other `setting`-kind state key) turns it on, and even on, an
update is offered, never applied without the operator's own click -
"Install 0.1.9 (sha256 checked)?" with what changed (the manifest can
carry a one-line summary, or just point at the real changelog: the
HANDOVER.md entries this project already writes for every release).
Matches `docs/ham/DESIGN-HAM.md`'s existing "Brian sole tester, opt-in"
decisions for other background behaviour (spotting) - same shape of
decision, same answer likely fits.

### Decisions for Brian

1. **New signing key, or reuse the Azure Trusted Signing identity for
   the manifest too?** This note assumes a new, separate key (simpler,
   lower blast radius, no coupling to the Azure app registration's own
   lifecycle) but it is his call.
2. **Where the key's private half lives and who/what can sign a
   manifest** - presumably `release.sh` itself, on shack, at release
   time, the same trust boundary as everything else that script does
   unattended already.
3. **Auto-check cadence, if any** (on launch? a daily timer? only when
   asked?) and whether NB and HAM share one manifest (one file,
   `{"openhamshack-nb": {...}, "openhamshack-ham": {...}}`) or each gets its own -
   one file is less to keep in sync given they release independently
   but on the same cadence most of the time.
4. **Whether the Linux side ever runs `apt install` itself** (needs a
   privileged helper, Dock360-style) **or only ever tells the operator
   the command to run** - the latter is less to build and matches "no
   telemetry, no silent action" in spirit, at the cost of being less
   convenient.
5. **Whether this applies to OpenHamShack ATV/DATV/Teletext too** - the
   manifest shape and client code would be identical; only the
   question of whether to build it once, shared, or per-project is
   open, and this note did not survey those repos.
