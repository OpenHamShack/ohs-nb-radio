# The Corresponding Source for the third-party GPL and LGPL code inside the
# Windows installers, one tarball per line. It is published on the shared
# source site, https://openhamshack.com/source/ (/srv/source-site on
# the release host; docs/source-site.md), which from 06/10/2026 serves every OpenHamShack
# project's third-party source - each tarball once, however many
# installers carry it - in place of a source/ folder on each product site.
# tools/release.sh [nb|ham] --windows publishes this list there as the
# manifest openhamshack-nb or openhamshack-radio (tools/source-site.py publish
# --carried-by NB or HAM: the lines whose "installers" field names that
# app), refuses to publish an installer until every tarball is there and
# verified, and the product page links to the app's section of that site.
#
# One list for both apps rather than one each: almost every line is
# carried by both, and two copies would be two places to forget a re-pin.
# The installers field already says which app carries what, so it is the
# split - which makes it load-bearing: name each app ("NB", "HAM") as a
# word in it, as Paramiko's line names only HAM.
#
# Why host them rather than point upstream: GPL-3 section 6 and the LGPL
# let a distributor point elsewhere only while that elsewhere stays up, for
# as long as the binaries are offered; SourceForge mirrors, Qt's archive
# moves and GitHub tag archives have all changed under people before. A
# copy on our own server is the one we can vouch for.
#
# This list is exactly what the NEXT installers to be published carry -
# from 0.1.4, each site offers only its newest installer. The GPL and LGPL
# oblige us to offer the source of what we distribute, for as long as we
# distribute it; with one installer on offer per site, that is one matching
# set of tarballs per app, not a pile kept for every .exe ever published.
# When release.sh --windows publishes an installer it moves the older .exe
# files off that site, then rebuilds the source site, which moves any
# tarball no manifest names any more into /srv/source-site-archive (never
# deleted). So a pin that changes is simply replaced here; but change this
# list only for an installer you are about to build - the other app's
# manifest stays as it is until its own next installer goes up, and that
# installer is built from this list.
#
# Fields, separated by "|" (spaces around them are trimmed):
#   file | sha256 | licence | installers that carry it | what it is the source of | url [fallback url ...]
# A line starting ">" is prose shown on the source site under the list.
#
# How each was identified (05/10/2026), so the next person can redo it:
#   - Qt 6, PyQt6: packaging/windows/requirements.txt pins PyQt6 6.11.0
#     and PyQt6-Qt6 6.11.2; the module list is what PyInstaller put in
#     _internal\PyQt6\Qt6 of the 0.1.3 build on the Windows build machine (Core, Gui, Network,
#     Widgets, Svg, Pdf, plugins, translations). Qt6Pdf.dll and the qpdf
#     image-format plugin are built from the Qt WebEngine module, so 0.1.3
#     needed the 580 MB qtwebengine tarball listed here. Neither program
#     uses them (PyInstaller's QtGui hook collects every image-format
#     plugin), so from 0.1.4 the specs leave them out
#     (packaging/windows/bundle_prune.py), build-windows.ps1 fails a
#     build where either reappears, and the line is gone. Should Qt PDF
#     ever be wanted, qtwebengine-everywhere-src-6.11.2.tar.xz (sha256
#     6101c1aa00ff933d1b65ee5d167f76e8d71b9ac5b378b0111277723ebda7c163,
#     Qt's archive/qt/6.11/6.11.2/submodules/) must come back first.
#   - codec2: freedv-gui v1.9.9.2's cmake/BuildCodec2.cmake builds tag
#     1.2.0, and libcodec2.dll comes from that release's installer.
#   - WSJT-X 2.7.0 and its DLLs (Qt 5.15.2's Qt5Core, FFTW 3.3.10, GCC
#     8.1.0's libquadmath) were carried from 0.1.4 until 17/10/2026, and
#     listed here; the manifests already published for the installers that
#     carried them keep their lines.
#   - dfu-util.exe inside ADI's driver package reports "dfu-util 0.8" and
#     has libusb linked in statically; its libusb_get_version() table reads
#     1.0.19 (nano 10903, which libusb-1.0.19's version_nano.h confirms).
#     It is not byte-identical to dfu-util's own 0.8 Windows binaries, so
#     ADI built it; ADI publishes no build files for it.
#   - rtlsdr.dll (Radio only) is ours: tools/build-rtlsdr-windows.sh
#     cross-builds it from exactly these two tarballs (their hashes are
#     pinned there too), against the UCRT, with libusb, libgcc and
#     winpthreads linked in. The RTL-SDR Blog's own Release.zip build was
#     not used: it needs msvcr100.dll, the VC++ 2010 runtime, which has
#     had no security updates for years.
#   - The hashes of the Qt tarballs match Qt's md5sums.txt; libusb
#     and PyQt6 (PyPI's digest) match their publishers' own.
